# Travel graph plan

Replaces the hand-typed `moves` and `destinations` strings of every stage in `src/data/zones.js` with a **graph computed from map coordinates**. Agreed with the author on 2026-11-19. **Built 2026-11-19: steps 1-3, 5 and a PNG overlay; the game still uses the old strings (step 6 waits for the author).** See "Built" at the end.

## Why

The old lists are typed by hand: they disagree with each other (one-way doors by accident), nothing checks them against the map, and a per-zone table is too coarse (not all Prairie scenes are near the Castle). The author also plans **dynamic scenes** (hand-made special scenes stay as fixed anchors, the scenes in between are composed on the fly; see `docs/SCENES.md`, `docs/ideas/world.md`), where the number of scenes of a trip must come from a realistic "travel time".

## Decisions (author, 2026-11-19)

| Topic | Decision |
|---|---|
| Approach | **A graph (nodes and edges) with Dijkstra, not a grid mask and not a polygon.** Only the coordinates of each scene are stored; edges are generated |
| Rivers | **Rivers block or cost a lot;** bridges are the crossings. Movement is reduced, not forbidden: water edges get a weight (soft cost) |
| Rocky areas | **Walkable on foot** (mountains are not walls) |
| Sea and lake | Effectively blocked (huge cost), only rivers are soft. One number if the author wants the sea passable at a high cost |
| Future | The graph answers "what does a trip between two map points cost", the same question the dynamic scenes need. **Build it now, do not wait for the dynamic scenes** |
| Palm sand beach | It is the Dunes' own beach (`las_Dunas`), reachable only from the surrounding zones. `la_playa` is the north-east beach |

## The model

- **Nodes:** every scene at its map x,y (the stage x,y already in `places`), plus **waypoint nodes**: the three bridges (Swamp, Prairie spring, south road), the fisher's pier, the stairs and portals (layer changes), the cave and mine mouths.
- **Edges are generated by code:** two nodes get an edge if they are within the search distance. Edge cost = length in map pixels, adjusted by terrain read from the map art by sampling along the line:
  - road pixel (a bridge counts as road): less than 1 (start guess 0.5)
  - land: 1
  - river: a **flat penalty per crossing** (a river is 1 px thin; start guess +60 px of walking), none on a bridge
  - sea or lake: per-pixel multiplier, huge (start guess x50)
- **Dijkstra over the graph:** about 100 nodes, so it is instant. Run offline into a generated file (`src/data/travelGraph.js`, never hand-edited), so the game does no pathfinding while it runs.
- **Layers:** the ground, aboveground and underground maps are three sets of nodes; a stair, portal or cave mouth is an edge between two nodes of different layers, with its own cost (the stairs and portals carry a big cost, so Heidan is far).
- **Nothing is ever disconnected** (soft costs), so the checker needs no waypoint repairs for pockets.

## The interface (keep it stable, the future builds on it)

- `travelCost(a, b)`: cheapest cost between two map points (in map pixels of walking).
- `route(a, b)`: the cheapest path as a list of map points.
- Today's adapter: `destinations(stage)` = the anchor scenes whose cost is under one limit (`config.js`). The old `destinations` and `moves` strings go away.
- Later (dynamic scenes): number of scenes of a trip = `ceil(cost / sceneLength)`, `sceneLength` one constant in `config.js` (placeholder now, calibrated then). The scenes in between are positions along `route(a, b)`, one scene length apart, with the anchors at the ends; the terrain at each position tells the heuristic which kind of scene to compose (a bridge scene on a bridge, a beach scene on the beach).

## Build order

1. **Graph generator** (tool, e.g. `tools/travel_graph.py`): reads the three maps and the stage coordinates and writes the generated file. Terrain colours (road, water, bridge planks) classified from the art; the multipliers live in `config.js`.
2. **`travelCost` and `route`** and the **adapter** so the game keeps working with the same destinations as the derived result.
3. **Checker** (same tool): one-way links, spots in the sea (snap to the nearest land and warn), scenes unreachable at a sane cost, a restricted place (the Dunes' beach) reachable from outside its zones.
4. **Overlay** in the dev tools (a mode or in Art mode): the map with the cheapest paths from a chosen scene, to judge the numbers by eye.
5. **Comparison** with the current hand-made strings: calibrate the limit and the penalties until the derived destinations match the old ones closely; the author reviews only the differences.
6. Switch the game to the derived destinations; remove the old strings.

Leave for later: creating the in-between scenes, how they are composed and chosen, the scene length, and how the wizard starts and stops a journey (design, for thinker). Keep the graph free of any scene count.

## Open questions

## Manual links are the graph (2026-11-20)

The author's decision: his manual links (travel.json) are the graph, not corrections over an automatic one. `moves()` and `destinations()` now come only from them and `travel.js` uses them (step 6 for the lists). Accessible and Difficult both count, Impossible does not; a point that is not a stage (bridges, mouth `_under` points, stairs) passes the trip to the stages linked to it; a stage with no link uses the old typed string. The future scenes became numbered stages (la_Pradera7-14, la_Mina6-7, la_Cueva6, el_Volcan6, el_Duenon6, el_Pantano6-7, el_Heidan6-11, la_Pradera6) with art in img/places/<zone>/; the beach points (la_playa1-6) have no zone yet, so they stay points. The automatic edges are still generated for the dev tools' costs and drawing. **Keep the pathfinder (`travelCost`, `route`, the generator) even though the lists no longer use it:** the author wants it later for other purposes, for example the story, to walk the wizard from his region to the region where a story beat happens.

## The data file (2026-11-25)
Everything the tool saves is in `src/data/travel.json`: `saved` (the stamp of the last save), `verdicts`, `positions` (scenes and waypoints moved by hand), `points` (added points) and `kinds` (scene types). `tools/serve.py` writes it as the tool sends it (no filtering), keeps the old file in `docs/travel-backups/`, refuses a save from a page loaded before the last save, and rebuilds the graph (`tools/travel_graph.py`, which stops with a message if the file is damaged). `src/data/travelOverrides.js` only loads the file for the game and the tool.
